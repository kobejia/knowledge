# 仓库文档生成 Skill 设计

## 背景

当前仓库已经通过 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md` 定义知识文档的内容标准，但不同生成工具并不一定主动读取或完整执行这些规范。结果是同一仓库中的文档可能在研究深度、事实表达、引用、Markdown 结构、导航维护和示例质量上不一致。

本设计将这些现有规范接入一个仓库级 skill。skill 不取代规范文件，而是负责识别任务、加载正确上下文、选择合适的生成流程并执行发布前检查。

## 目标

- 仓库内创建或实质修改文档时，稳定触发同一套生成流程。
- 让深度知识文档、轻量清单和 README 等导航文档采用与用途匹配的约束强度。
- 继续以 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md` 作为内容规范的唯一事实来源，避免多份规则漂移。
- 统一 Markdown 产物的结构、链接、元信息和仓库导航检查。
- 仅在用户明确要求时生成 JavaScript、CSS、HTML 等配套 Demo，并确保 Demo 与正文结论一致且经过真实验证。
- 用可复现的测试场景验证 skill 能纠正不同工具常见的不一致行为。

## 非目标

- 不覆盖 Word、PDF、PPT、电子表格或其他二进制文档格式。
- 不自动为技术文档创建 Demo。
- 不把所有文档强制改造成同一种章节模板。
- 不复制或重新定义编辑指南和读者画像中的内容原则。
- 不在首版引入复杂的文档构建系统、内容管理系统或全仓库强制校验流水线。

## 方案

采用单一编排型 skill：

```text
.agents/skills/generating-knowledge-documents/
├── SKILL.md
├── references/
│   ├── markdown-quality.md
│   └── demo-quality.md
└── evals/
    └── evals.json
```

`SKILL.md` 负责触发条件、文档分类、必读上下文、工作流程和完成条件。两份 reference 只承载格式或产物类型特有的检查，避免主文件过长，也避免重复仓库已有的编辑原则。

## 触发范围

当任务在当前仓库内创建或实质修改以下内容时使用该 skill：

- 深度知识文档或专题文章；
- 资料清单、目录、索引和研究笔记；
- README、知识地图及其他导航文档；
- 用户明确要求的配套 HTML、CSS、JavaScript Demo；
- 对上述产物进行扩写、重构或质量修订。

纯拼写修正、机械格式化或不影响内容语义的微小编辑可以不启动完整研究流程，但仍应遵守对应文件的局部格式。

## 文档分类与约束强度

### 深度主题文档

完整读取并执行 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md`。根据领域选择 `survey`、`deep-dive` 或 `expert`，围绕核心问题、模型、演化、取舍、边界和证据组织内容，并维护最小 YAML 元信息与 README 知识地图。

### 轻量资料文档

适用于清单、目录、资料汇总和简短研究记录。保留可靠来源、事实与推论边界、清楚的字段或分组结构，但不强制加入深度文章的模型、演化和完整论证章节。文档结构服从资料用途。

### README 与导航文档

强调准确导航、简洁说明和链接有效性。只在内容地图发生变化时同步更新，不把 README 扩写成正文摘要集合。

### 配套 Demo

只有用户明确要求时创建。Demo 必须能验证正文中的某个运行模型、边界、反例或方案取舍；不得为了显得完整而扩张为无关的示例项目。

## 工作流程

1. 确认任务涉及的文档类型及是否明确要求 Demo。
2. 读取仓库根目录的 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md`，再读取目标文件与相邻上下文。
3. 为时效性事实、专业结论和争议性判断查阅合适的一手或权威来源。
4. 按文档类型选择约束强度并生成或修改内容。
5. 对 Markdown 执行专项检查：元信息、标题层级、代码块、表格、链接、引用邻近性和 README 导航一致性。
6. 若用户明确要求 Demo，读取 Demo 专项规范，保持文件职责清楚，并执行真实运行或浏览器验证。
7. 复查正文与 Demo 是否表达同一套模型、前提和边界。
8. 运行适合当前变更的机械检查，并在交付时说明验证范围与尚未验证的部分。

## 专项参考文件

### `references/markdown-quality.md`

只包含 Markdown 特有且可操作的规则，包括：

- YAML 元信息适用范围与字段一致性；
- 标题层级、列表、表格和代码块的可读性；
- 相对链接、锚点和 README 知识地图的一致性；
- 引用与所支持陈述之间的邻近关系；
- Markdown lint 或轻量脚本能够自动发现的问题；
- 不为统一格式牺牲主题自然结构的边界。

### `references/demo-quality.md`

只在用户明确要求 Demo 时读取，包括：

- Demo 必须对应正文中的明确学习或验证目标；
- HTML、CSS、JavaScript 文件的职责和最小结构；
- 避免无关依赖、装饰性功能和未经解释的抽象；
- 可运行性、控制台错误、关键交互和不同视口的验证；
- 正文与代码的术语、行为、限制及失败模式一致性；
- 无法运行或验证时必须明确披露，不能宣称完成验证。

## 错误与不确定性处理

- 缺少主题边界但可由仓库上下文安全推断时，采用最小合理假设并明确记录。
- 选择 `survey`、`deep-dive` 或 `expert` 存在实质歧义时再询问用户。
- 无法访问可靠来源时，不补造事实；缩小结论范围或标记尚未确认。
- Demo 无法启动、依赖缺失或浏览器验证失败时，保留证据并报告未完成状态。
- 目标文件已有未提交改动时，先读取并保留用户修改，不覆盖无关内容。

## 测试策略

skill 按测试驱动方式创建。先在无 skill 条件下运行真实任务提示，记录基线中的遗漏，再编写最小 skill 并复测。

首轮测试覆盖：

1. 创建前端专家深度 Markdown 文档，检查是否读取读者画像、避免入门堆砌、使用最小元信息并维护 README。
2. 扩充一个带官方来源的轻量资料清单，检查是否避免套用深度文章模板，同时保留来源与分类结构。
3. 用户明确要求创建 HTML/CSS/JavaScript Demo，检查是否读取 Demo 规范、实际验证并保持正文与代码一致。
4. 用户只要求生成技术知识文档但未要求 Demo，检查 skill 是否避免自行创建示例项目。

客观检查与人工评审结合：客观检查覆盖文件存在性、元信息、链接、README 更新和 Demo 可运行性；人工评审覆盖模型质量、取舍、边界、信息密度与正文和 Demo 的一致性。

## 完成标准

- skill 位于仓库 `.agents/skills/generating-knowledge-documents/` 并能被项目级发现。
- frontmatter 的名称和描述能覆盖文档创建、文档修改、Markdown、知识文章、资料清单、README 和显式 Demo 请求等触发语境。
- `SKILL.md` 不复制现有规范，而是明确要求读取它们。
- Markdown 与 Demo 专项规则按需加载，且没有互相冲突的要求。
- 无 skill 的基线行为已经记录；加入 skill 后，测试场景中的关键遗漏得到纠正。
- 所有机械检查通过，测试结果和仍需人工判断的项目均有记录。
