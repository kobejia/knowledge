# 仓库文档生成 Skill 设计

## 背景

当前仓库已经通过 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md` 定义知识文档的内容标准，但不同生成工具并不一定主动读取或完整执行这些规范。结果是同一仓库中的文档可能在研究深度、事实表达、引用、Markdown 结构、导航维护和示例质量上不一致。

本设计将这些现有规范接入一个仓库级 skill。skill 不取代规范文件，而是负责识别任务、加载正确上下文、选择合适的生成流程并执行发布前检查。

## 目标

- 仓库内创建或实质修改文档时，稳定触发同一套生成流程。
- 生成前先确认对用户输入的理解，再由用户选择内容档位；有实质歧义时先给出明确选项消歧。
- 让深度知识文档、轻量清单和 README 等导航文档采用与用途匹配的约束强度。
- 继续以 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md` 作为内容规范的唯一事实来源，避免多份规则漂移。
- 统一 Markdown 产物的结构、链接、元信息和仓库导航检查。
- 对技术主题主动确认是否需要 JavaScript、CSS、HTML 等配套 Demo 与练习题；非技术主题跳过该步骤。
- 确保生成的 Demo 与正文结论一致且经过真实验证，练习题与所选档位和正文内容一致。
- 用可复现的测试场景验证 skill 能纠正不同工具常见的不一致行为。

## 非目标

- 不覆盖 Word、PDF、PPT、电子表格或其他二进制文档格式。
- 不在用户确认前为技术文档创建 Demo 或练习题。
- 不把所有文档强制改造成同一种章节模板。
- 不复制或重新定义编辑指南和读者画像中的内容原则。
- 不在首版引入复杂的文档构建系统、内容管理系统或全仓库强制校验流水线。

## 方案

采用单一编排型 skill：

```text
.agents/skills/generating-knowledge-documents/
├── SKILL.md
├── references/
│   ├── markdown-quality.md
│   ├── demo-quality.md
│   └── exercise-quality.md
└── evals/
    └── evals.json
```

`SKILL.md` 负责触发条件、文档分类、必读上下文、工作流程和完成条件。两份 reference 只承载格式或产物类型特有的检查，避免主文件过长，也避免重复仓库已有的编辑原则。

## 触发范围

当任务在当前仓库内创建或实质修改以下内容时使用该 skill：

- 深度知识文档或专题文章；
- 资料清单、目录、索引和研究笔记；
- README、知识地图及其他导航文档；
- 用户确认需要的配套 HTML、CSS、JavaScript Demo 与练习题；
- 对上述产物进行扩写、重构或质量修订。

纯拼写修正、机械格式化或不影响内容语义的微小编辑可以不启动完整研究流程，但仍应遵守对应文件的局部格式。

## 生成前交互

### 理解与消歧

先基于用户输入判断主题、目标和产物范围：

- 如果存在实质歧义，例如主题边界不明确、存在多个合理方向或产物要求互相冲突，向用户提供简洁、互斥的选项并等待选择。
- 如果不存在实质歧义，用一至两句话介绍对用户输入内容的理解，不额外要求用户设计目录。

### 选择内容档位

在理解一致后，由用户从四个档位中选择：

| 档位 | 定位 | 内容边界 |
| --- | --- | --- |
| 专家 | 对应 `expert` | 跳过常规入门，聚焦运行模型、架构演化、设计取舍、生产约束、失败模式和前沿问题。 |
| 入门 | 基础介绍 | 建立必要概念、基本用法和最小可用理解，不展开全面论证或高级边界。 |
| 全面 | 对应 `deep-dive` | 从必要基础逐步进入核心模型、证据、主要分歧、取舍、反例和现实边界。 |
| 了解 | 对应 `survey` | 建立视野地图，包含理解主题所需的入门内容、主题包含的主要部分、价值与关键问题，但不深入实现或完整论证。 |

这四档将成为 `EDITORIAL_GUIDE.md` 与 `READER_PROFILE.md` 中的规范定义；skill 只负责展示选择并按选定档位执行，避免出现两套深度语义。

### 技术主题的产物确认

完成档位选择后判断主题是否属于技术类：

- 技术类：询问用户是否需要 Demo 和练习题。两个选项应分别确认，允许只选其一、两者都选或都不选。
- 非技术类：跳过 Demo 和练习题确认，直接进入文档生成。

## 文档分类与约束强度

### 深度主题文档

完整读取并执行 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md`。按照用户选择的“专家、入门、全面、了解”档位控制起点与深度，围绕该档位需要的核心问题、模型、演化、取舍、边界和证据组织内容，并维护最小 YAML 元信息与 README 知识地图。

### 轻量资料文档

适用于清单、目录、资料汇总和简短研究记录。保留可靠来源、事实与推论边界、清楚的字段或分组结构，但不强制加入深度文章的模型、演化和完整论证章节。文档结构服从资料用途。

### README 与导航文档

强调准确导航、简洁说明和链接有效性。只在内容地图发生变化时同步更新，不把 README 扩写成正文摘要集合。

### 配套 Demo

只有技术主题且用户在生成前确认需要时创建。Demo 必须能验证正文中的某个概念、运行模型、边界、反例或方案取舍；不得为了显得完整而扩张为无关的示例项目。

### 配套练习题

只有技术主题且用户在生成前确认需要时创建。题目服务于理解检查和知识迁移，难度与所选档位一致；答案或提示必须能由正文推导，不能考查正文未覆盖的偶然细节。

## 工作流程

1. 理解用户输入；存在实质歧义时给出选项请用户选择，否则用一至两句话介绍所理解的内容。
2. 请用户选择“专家、入门、全面、了解”之一。
3. 判断是否为技术主题；技术类分别确认是否需要 Demo 和练习题，非技术类跳过。
4. 确认任务涉及的文档类型和产物范围。
5. 读取仓库根目录的 `EDITORIAL_GUIDE.md` 和 `READER_PROFILE.md`，再读取目标文件与相邻上下文。
6. 为时效性事实、专业结论和争议性判断查阅合适的一手或权威来源。
7. 按用户选择的档位和文档类型生成或修改内容。
8. 对 Markdown 执行专项检查：元信息、标题层级、代码块、表格、链接、引用邻近性和 README 导航一致性。
9. 若用户选择 Demo，读取 Demo 专项规范，保持文件职责清楚，并执行真实运行或浏览器验证。
10. 若用户选择练习题，读取练习题专项规范，检查覆盖范围、难度、可作答性以及答案与正文的一致性。
11. 复查正文、Demo 与练习题是否表达同一套概念、前提和边界。
12. 运行适合当前变更的机械检查，并在交付时说明验证范围与尚未验证的部分。

## 专项参考文件

### `references/markdown-quality.md`

只包含 Markdown 特有且可操作的规则，包括：

- YAML 元信息适用范围与字段一致性；
- 标题层级、列表、表格和代码块的可读性；
- 相对链接、锚点和 README 知识地图的一致性；
- 引用与所支持陈述之间的邻近关系；
- Markdown lint 或轻量脚本能够自动发现的问题；
- 不为统一格式牺牲主题自然结构的边界。

### `references/demo-quality.md`

只在技术主题且用户确认需要 Demo 时读取，包括：

- Demo 必须对应正文中的明确学习或验证目标；
- HTML、CSS、JavaScript 文件的职责和最小结构；
- 避免无关依赖、装饰性功能和未经解释的抽象；
- 可运行性、控制台错误、关键交互和不同视口的验证；
- 正文与代码的术语、行为、限制及失败模式一致性；
- 无法运行或验证时必须明确披露，不能宣称完成验证。

### `references/exercise-quality.md`

只在技术主题且用户确认需要练习题时读取，包括：

- 题目覆盖正文的关键概念、模型或操作，不考查正文之外的冷知识；
- 难度和抽象程度匹配“专家、入门、全面、了解”档位；
- 组合概念检查、应用题和边界分析，避免机械复述；
- 每题提供可核对的答案、解析或评价标准；
- Demo 与练习题同时存在时，允许围绕 Demo 设计观察和修改任务，但不能依赖未验证行为。

## 错误与不确定性处理

- 仅缺少不影响方向的次要信息且可由仓库上下文安全推断时，采用最小合理假设并明确记录；会改变主题方向或产物范围的缺失信息必须先消歧。
- 对主题、范围或产物存在实质歧义时先提供选项；档位始终由用户选择，不由 skill 静默推断。
- 无法访问可靠来源时，不补造事实；缩小结论范围或标记尚未确认。
- Demo 无法启动、依赖缺失或浏览器验证失败时，保留证据并报告未完成状态。
- 目标文件已有未提交改动时，先读取并保留用户修改，不覆盖无关内容。

## 测试策略

skill 按测试驱动方式创建。先在无 skill 条件下运行真实任务提示，记录基线中的遗漏，再编写最小 skill 并复测。

首轮测试覆盖：

1. 输入明确的前端主题，检查是否先用一至两句话复述理解，再提供四档选择，并在选择“专家”后避免入门堆砌。
2. 输入存在多个合理方向的主题，检查是否先给出互斥选项消歧，而不是直接生成目录或正文。
3. 选择“了解”档创建技术 Markdown 文档，检查是否建立视野地图并包含必要入门内容，同时避免进入全面论证。
4. 扩充一个带官方来源的轻量资料清单，检查是否避免套用深度文章模板，同时保留来源与分类结构。
5. 技术主题选定档位后，检查是否分别确认 Demo 和练习题；选择两者后，检查 Demo 已实际验证、练习题难度匹配且三类产物一致。
6. 技术主题选择不需要 Demo 和练习题后，检查 skill 是否避免自行创建相关产物。
7. 非技术主题选定档位后，检查是否跳过 Demo 与练习题确认并直接进入生成流程。

客观检查与人工评审结合：客观检查覆盖文件存在性、元信息、链接、README 更新、Demo 可运行性和练习题答案完整性；人工评审覆盖模型质量、取舍、边界、信息密度以及正文、Demo 与练习题的一致性。

## 完成标准

- skill 位于仓库 `.agents/skills/generating-knowledge-documents/` 并能被项目级发现。
- frontmatter 的名称和描述能覆盖文档创建、文档修改、Markdown、知识文章、资料清单、README、Demo 和练习题等触发语境。
- skill 在生成前稳定执行“理解或消歧 → 用户选择档位 → 技术主题确认 Demo 与练习题”的交互顺序。
- `EDITORIAL_GUIDE.md` 与 `READER_PROFILE.md` 对四档的名称、语义和内部标识保持一致。
- `SKILL.md` 不复制现有规范，而是明确要求读取它们。
- Markdown、Demo 与练习题专项规则按需加载，且没有互相冲突的要求。
- 无 skill 的基线行为已经记录；加入 skill 后，测试场景中的关键遗漏得到纠正。
- 所有机械检查通过，测试结果和仍需人工判断的项目均有记录。
