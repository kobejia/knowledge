# 现有知识文档重生成设计

## 背景

仓库现有四篇知识文档形成于 `personal-learn` 五档、画像适配、知识索引和可视化规范完成之前。它们已经具备可复用事实和部分可靠来源，但结构、论证深度、图表密度与新规范不完全一致。本轮按新 skill 原地重新生成内容，不改变知识树分类和文件路径。

## 目标

- 原地重写知识索引中的四篇现有文档。
- 保留经重新核实仍然有效的事实、判断和一手来源，重建不符合新规范的结构。
- 结合当前画像调整前置解释、术语密度、例子和推理跨度。
- 用 Mermaid、Markdown 表格和文本树表达架构、层次、流程、状态、演化和取舍。
- 所有时效性事实、技术行为、规则与争议使用一手或权威来源就近支撑。
- 更新 Markdown 后重新校验知识索引并构建离线预览。

## 非目标

- 不移动、拆分或新增知识文档。
- 不修改 `personal-learn-config.yaml` 或知识分类树。
- 不生成 Demo、练习题或其他配套实践。
- 不把 README 恢复为知识地图。
- 不处理现有 `.DS_Store` 文件。
- 不以统一章节模板或固定图表数量替代主题自身结构。

## Skill 调用边界

- 只有用户显式调用某个 skill，或助手先说明具体 skill、用途和影响并得到用户确认后，才能使用该 skill。
- 不得仅因任务与 skill 描述匹配、skill 已安装或助手认为有帮助而自动启用。
- 一次确认只授权当次明确说明的 skill 和任务范围，不自动授权其他 skill，也不延续到后续独立任务。
- 需要新增或切换 skill 时必须再次说明并等待确认；在确认前继续使用普通能力完成不依赖该 skill 的工作，确实无法继续时报告阻塞。
- 用户本轮明确要求“按照 skills 的要求”重新生成现有知识，因此 `personal-learn` 已获得本轮授权；该授权不包含其他 skill。

## 固定范围

| 文档 | 路径 | 档位 | 归类 |
| --- | --- | --- | --- |
| Vue 状态管理演进 | `learn/frontend/vue/vuex-pinia.md` | 专家 `expert` | 沿用现有索引 |
| Chrome Extension 架构 | `learn/frontend/browser/chrome-extension-architecture.md` | 专家 `expert` | 沿用现有索引 |
| Codex 高效协作 | `learn/ai/tools/codex-high-efficiency-guide.md` | 全面 `deep-dive` | 沿用现有索引 |
| 奖项与荣誉清单 | `learn/reference/awards/awards-catalog.md` | 全面 `deep-dive` | 沿用现有索引，frontmatter 从 `survey` 更新为 `deep-dive` |

四篇文档保留原 `created`，将 `updated` 更新为 `2026-08-01`。JSON 中的标题与 frontmatter 标题必须继续逐字一致；如正文 H1 为增强论证而变化，不得破坏该契约。

## 采用方式

采用“重构式重写”：先提取旧文档中值得保留的事实、来源和判断，再基于当前问题重新搭建解释模型。旧目录不作为强制骨架；未经重新核实的数字、版本结论、推荐和制度描述不得直接迁移。

不采用仅补图和润色的保守修订，因为它无法修复旧文档的模型与证据缺口；也不采用完全丢弃旧资料的空白重写，因为这会浪费已验证来源并增加遗漏风险。

## 各文档内容设计

### Vue 状态管理演进：专家档

核心问题是：Vuex 与 Pinia 如何建立在 Vue 响应式和依赖注入之上，它们的架构差异为何出现，又怎样影响大型应用的状态边界和生产约束。

重点覆盖：

- Vuex 与 Pinia 的真实运行模型、根容器和 Store 生命周期；
- 单一状态树、模块注册与独立 Store 组合之间的结构差异；
- mutation、action、响应式追踪与开发工具的关系；
- TypeScript 推断的改善及其边界；
- SSR、请求隔离、hydration、插件、持久化与跨 Store 依赖；
- 从 Vuex 迁移到 Pinia 的兼容策略、渐进路径和不适合迁移的情况；
- 重复 ID、循环依赖、解构丢失响应性、状态泄漏等生产失败模式。

优先图表：运行时组件图、状态更新时序图、Vuex/Pinia 结构对比、SSR 请求隔离流程。

### Chrome Extension：专家档

核心问题是：扩展不是“拥有更多 API 的网页”，而是多个生命周期和信任等级不同的执行上下文组成的事件驱动系统。

重点覆盖：

- 页面、content script、service worker、扩展 UI、存储和外部服务的上下文边界；
- service worker 的终止、唤醒、状态恢复和幂等设计；
- 消息作为内部协议时的验证、授权、关联、超时和错误语义；
- host permissions、optional permissions、activeTab 与用户授权模型；
- CSP、远程代码限制、页面输入与特权能力隔离；
- 声明式 API 和命令式能力的控制权取舍；
- 页面增强器、浏览伴侣、DevTools 扩展、网络策略扩展等架构适用条件；
- 生命周期错觉、协议漂移、状态竞争、权限膨胀和商店审核失败。

优先图表：系统上下文图、信任边界图、消息时序图、service worker 恢复状态机、权限决策流程。

### Codex：全面档

核心问题是：如何把 Codex 作为可审计的任务执行协作者，而不是把它当成一次性文本生成器。

重点覆盖：

- 任务、上下文、工具、权限、计划、实现和验证之间的运行模型；
- 明确目标、边界、输入、输出和完成证据的方法；
- 解释、诊断、修改、研究、长期任务等不同请求的工作流差异；
- skills、配置、计划、worktree、测试和代码审查的职责边界；
- 上下文选择、渐进披露与避免无关读取；
- 自动化程度、人工判断、可逆性和外部副作用之间的取舍；
- 常见失败：模糊授权、未经验证的完成声明、过度扩张、机械模板和上下文污染；
- 从简单任务到复杂仓库协作的渐进使用方式。

内容以当前官方 OpenAI/Codex 文档为主要依据，不把当前客户端行为推断成永久产品契约。

优先图表：任务生命周期、权限与验证闭环、工作模式选择流程、skill/配置/计划的层次关系。

### 奖项与荣誉：全面档

核心问题是：如何建立一份可维护、可追溯、不会混淆奖项、荣誉称号、资格和榜单的参考目录。

重点覆盖：

- 奖项、勋章、荣誉称号、职业资格、榜单和商业认证的边界；
- 主办机构、提名、评审、授予、届次、类别和获奖对象等制度结构；
- 国际与中国大陆代表性奖项的领域分类和官方来源；
- 官方制度文件、主办方页面、结果公告与二手报道的证据层级；
- 更名、停办、类别变化、联合主办和历史沿革的维护方式；
- 代表性、地域偏差、制度差异、政治与商业因素带来的解释限制；
- 当前目录的覆盖范围、明确缺口和后续扩展原则。

保留现有有效条目，但重新核查明显时效性、定义性和制度性陈述。不得宣称目录穷尽所有奖项。

优先图表：概念边界图、奖项制度生命周期、来源可信度阶梯、分类体系；大量重复字段继续使用表格。

## 画像适配

Vue、浏览器和 JavaScript 属于画像明确熟悉的领域，专家文档跳过常规安装、基础 API 和面向初学者的用法清单，直接进入运行模型、架构取舍与复杂失败。

Codex 属于与软件工程相邻的 AI 工具领域。全面档可以借助熟悉的工程工作流建立连接，但必须说明任务代理与传统构建工具在不确定性、权限和完成证据上的差异。

奖项与荣誉没有被画像声明为熟悉领域。全面档先建立必要制度概念和证据语言，再进入分类、争议和维护方法，不假设用户拥有法学、公共管理或行业评奖经验。

## 来源与研究

- Vue/Pinia：优先 Vue、Vuex、Pinia 官方文档与源码，必要时引用正式迁移或维护说明。
- Chrome Extension：优先 Chrome for Developers、Chromium 设计资料和相关 Web 标准。
- Codex：优先当前 OpenAI 官方 Codex 文档；查证日期写入文档。
- 奖项：优先主办机构、政府部门、专业协会、法律政策文本和正式结果公告。

任何来源都必须直接支持相邻结论。版本、大小、生命周期时限、配额、官方推荐、奖项定位和制度状态必须重新查证；无法获得可靠支持时删除、收窄或标记不确定性。

## 可视化要求

- 图表数量由解释价值决定，不设最低数量。
- 每张图只回答一个主要问题，图前说明用途，图后解释阅读顺序、边界和结论。
- Mermaid 图必须在离线预览构建中实际转换为内联 SVG。
- 同一文档多图必须保持 SVG ID 隔离。
- 只在重复字段比较时使用表格，只在表达层级时使用文本树。
- 图表和正文共享术语、方向、状态与边界。

## 实施顺序

1. 逐篇盘点旧文档的可保留事实、来源、结构问题与待核实结论。
2. 按主题并行收集一手或权威来源，但逐篇完成写作与验证。
3. 先重写技术专家文档，再重写 Codex，最后处理奖项目录。
4. 每篇完成后检查 frontmatter、H1、标题层级、链接、引用和 Mermaid。
5. 四篇完成后运行知识索引校验和离线预览构建。
6. 在浏览器中逐篇检查导航、表格、代码块、图表、hash 和控制台。

## 测试与验收

- 四篇文档路径和知识索引 ID 不变。
- 指定档位正确，日期符合规则，JSON title 与 frontmatter title 一致。
- 技术专家文档达到机制、架构、生产约束和失败模式深度。
- 两篇全面文档覆盖必要基础、模型、证据、主要分歧、边界和连接。
- 关键时效性与制度性结论有邻近的权威来源。
- 不存在未经支撑的包体积、版本、配额、推荐或“最高/最权威”等绝对判断。
- Mermaid 全部实际渲染，图前后有解释，多图 ID 不冲突。
- `npm run validate:knowledge`、`npm run build:preview`、`npm test`、shell 契约测试和 `git diff --check` 全部通过。
- 离线预览能够显示四篇重写后的文档，导航与 hash 正常，控制台无预览自身错误。
