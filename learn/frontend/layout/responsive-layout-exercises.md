# 响应式布局专家练习：上下文、约束与验证

这组练习围绕[响应式上下文实验](./responsive-layout-demo/index.html)展开。先阅读[响应式布局：交付架构、布局机制与工程取舍](./responsive-layout.md)，再按以下闭环操作：

```text
运行 → 观察 → 推理 → 修改 → 验证
```

练习目标不是记住属性，而是建立三个判断：变化属于页面还是组件、连续约束是否已经足够、JavaScript 是否真的需要介入。

## 运行基线

1. 直接在现代 Chromium 浏览器中打开 `responsive-layout-demo/index.html`。
2. 保持浏览器视口宽度大于 `60rem`，把“可调宿主宽度”设为 `320px`。
3. 依次选择媒体查询、内在 Grid 和容器查询。
4. 记录两张卡片的列数、宿主状态与溢出状态。
5. 切换“长内容”和“RTL 内容”，确认控制台没有由 Demo 引起的错误。

## 练习一：先预测上下文耦合

在运行前填写下面的预测矩阵。假设页面视口为 `1280px`，主内容宿主约 `760px`，可调宿主为 `320px`。

| 策略 | 主内容宿主预计列数 | 可调宿主预计列数 | 判断依据 |
| --- | --- | --- | --- |
| 媒体查询 |  |  |  |
| 内在 Grid |  |  |  |
| 容器查询 |  |  |  |

运行 Demo 核对后，回答：媒体查询出现的“宿主错配”是 CSS bug、断点值不合理，还是上下文选择错误？如果把断点从 `60rem` 改为 `40rem`，根因是否消失？

<details>
<summary>答案与评价标准</summary>

预期结果：

| 策略 | 主内容宿主 | 320px 宿主 | 原因 |
| --- | --- | --- | --- |
| 媒体查询 | 两列 | 两列 | 两个组件看到同一个大于 `60rem` 的页面视口 |
| 内在 Grid | 两列 | 一列 | 每列至少需要 `17rem`，窄宿主容不下两列 |
| 容器查询 | 两列 | 一列 | 只有各自宿主达到 `34rem` 才进入两列 |

“宿主错配”是查询上下文错误，不是浏览器 bug。调整页面断点只能改变在哪些视口复现；只要组件宽度与视口宽度不等价，根因仍存在。优秀答案还应指出：如果组件只存在于一个由页面断点严格控制的区域，媒体查询并非错误；问题来自可复用组件的宿主不确定性。

</details>

## 练习二：制造并解释最小内容尺寸失败

选择“长内容与不可断标识符”，确认初始状态显示“无溢出”。然后在开发者工具中依次临时关闭：

1. `.card-body` 的 `min-inline-size: 0`；
2. `.card-token` 的 `overflow-wrap: anywhere`；
3. `.responsive-card` 双列规则中的 `minmax(0, 1fr)`，改为 `1fr`。

每次只改一项，观察 `scrollWidth`、轨道宽度和文本行为。解释三个声明分别控制的是项目下限、文本换行机会，还是轨道下限。

<details>
<summary>答案与评价标准</summary>

- `min-inline-size: 0` 允许 Grid/Flex 项目低于自动最小内容尺寸；它控制项目是否允许收缩。
- `overflow-wrap: anywhere` 为长标识符增加可用换行机会，从而降低其最小内容贡献。
- `minmax(0, 1fr)` 明确把轨道最小值设为零；单独的 `1fr` 轨道通常带有自动最小下限，可能被内容贡献撑开。

三者不是可随意互换的“防溢出技巧”。完整答案应从内容贡献 → 项目最小尺寸 → 轨道尺寸的顺序解释结果，并说明隐藏溢出不等于解决内容可达性。

</details>

## 练习三：从内容失败点推导容器阈值

Demo 使用 `34rem` 作为卡片从单列切到双列的容器阈值。不要假设它正确：

1. 列出双列状态的约束：媒体列宽、正文最小可读宽度、间距、边框和内边距。
2. 用这些约束计算一个初始阈值。
3. 在 `30rem` 到 `40rem` 之间调节宿主，使用常规、长内容和 RTL 三种样本验证。
4. 修改 `@container` 阈值，使它来自内容约束，而不是匹配某个设备宽度。

<details>
<summary>答案与评价标准</summary>

没有唯一数值答案。合格推导应形如：

```text
媒体列 12rem
+ 正文可用宽度约 18rem
+ 容器内边距、边框和列间距约 3rem
= 初始阈值约 33rem
```

随后用真实内容将阈值校准到相邻稳定区间。优秀答案会检查阈值前后而不是只看目标值，并说明正文最小宽度是产品可读性约束，不是某款平板的尺寸。

</details>

## 练习四：设计宿主契约，而不泄漏页面知识

假设卡片将被放入四个位置：文章主栏、280px 侧栏、可拖动面板和第三方微前端插槽。设计一个组件契约，至少说明：

- 哪个元素建立查询容器，是否需要命名；
- 组件的无查询基线；
- 哪些变化由内在 Grid 完成，哪些由容器查询完成；
- 宿主可以提供哪些设计令牌；
- 没有容器查询支持时如何保持核心内容可用。

限制：组件内部不能读取页面路由、设备名或全局 `.is-mobile` 类。

<details>
<summary>答案与评价标准</summary>

一个稳健契约可以是：宿主在插槽边界建立命名 `inline-size` 容器；组件默认单列并保持完整语义；卡片列表的列数由 `auto-fit/minmax()` 决定；卡片图文结构只在命名容器达到内容阈值时切换；颜色、间距和密度通过有默认值的自定义属性传入。

不支持容器查询时保留单列基线，因此损失的是增强后的密度，不是信息或操作。优秀答案还会避免让组件自己建立并查询同一个尺寸盒子，并说明嵌套容器中为什么需要名称。

</details>

## 练习五：判断 CSS 与 JavaScript 的职责

为以下需求选择机制，并说明为什么其他机制不合适：

1. 页面达到双栏空间时显示常驻目录。
2. 卡片进入窄侧栏时把图文改成单列。
3. Canvas 图表宿主变化后重设像素缓冲区。
4. 窗口进入 `prefers-reduced-motion: reduce` 后停止业务层自动播放。
5. 列表能放下几张最小宽度为 18rem 的卡片。
6. React 状态中维护 `isMobile`，只为了给根节点添加同名 CSS 类。

<details>
<summary>答案与评价标准</summary>

1. 媒体查询：这是页面级编排。
2. 容器查询：变化依赖组件实际宿主。
3. `ResizeObserver`：CSS 不能重绘 Canvas 的像素缓冲区；回调应避免尺寸反馈循环。
4. `matchMedia()`：业务行为需要与媒体偏好同步；视觉动画本身仍由 CSS 媒体查询关闭。
5. 内在 Grid：`repeat(auto-fit, minmax(min(100%, 18rem), 1fr))` 已能表达，无需离散查询。
6. 删除这层 JS 状态：它复制 CSS 已有状态，容易在 SSR、首次渲染和断点边界漂移。

优秀答案应区分“布局结果”和“布局结果引发的非 CSS 行为”，而不是笼统地说 JavaScript 更灵活。

</details>

## 练习六：从布局升级到交付架构

分别为下列产品选择“同一响应式页面、动态服务、独立 URL 或混合架构”，并列出必须验证的边界：

- 新闻正文：桌面与移动内容相同，但图片候选和编排不同。
- 仓库巡检终端：手持设备只执行扫码和确认，桌面端负责复杂规则编辑。
- 已运行十年的 `m.example.com`：内容大致相同，团队计划统一技术栈。
- 数据分析工作台：同一页面有可拖动面板、图表和嵌入卡片。

最后检查你的方案是否在窄屏时通过 CSS `order` 改变了任务顺序；如果改变，重写 DOM 或交互结构，使视觉、键盘和阅读顺序保持一致。

<details>
<summary>答案与评价标准</summary>

- 新闻正文：同一响应式页面；用媒体查询、响应式图片和内容回流。无需为相同内容制造服务端变体。
- 巡检终端：任务和信息架构根本不同，动态服务、独立应用或共享领域模型的混合架构都可能成立；选择取决于 URL、离线、权限和部署边界，不能只靠 CSS 隐藏桌面功能。
- 旧 m 站：目标通常是迁移到同一响应式 URL；需要逐 URL 重定向、canonical、内容与结构化数据核对以及监控，而不是立即删除旧站。
- 数据工作台：同一页面 + 页面媒体查询 + 面板容器查询 + 图表 `ResizeObserver`。面板空间与视口不等价。

评价重点是推理链是否从内容与任务差异出发，并覆盖缓存/索引、可访问顺序和失败回退；不是要求所有人选择完全相同的标签。

</details>

## 完成标准

- 能用“观察对象、变化对象、连续或离散”解释每种机制。
- 能从内容贡献解释自动最小尺寸和溢出，而不是只给经验修复。
- 能为页面和组件选择不同上下文，并设计无查询基线。
- 能说明 JavaScript 观察的必要条件与循环风险。
- 能把 CSS 布局问题与多端交付架构问题分开。
- 实际运行过三种策略、三类内容和窄/宽宿主，结论与 Demo 行为一致。
