# AI + Obsidian 全面练习：从 Vault 到可审计检索

这组练习与 [AI + Obsidian：从本地 Markdown Vault 到可验证的个人知识系统](obsidian-ai-knowledge-base.md) 共用一个目标：**能把 Vault 文件、派生索引、检索证据、模型上下文和写回权限分开，并通过可观察行为判断系统在哪一层失败。**

配套的 [Mini Vault RAG Lab](obsidian-ai-knowledge-base-demo/index.html) 使用虚构资料并完全离线运行。直接在浏览器打开 `index.html` 即可；页面修改只保存在内存，不会读取或写入你的真实 Obsidian Vault，也不会调用云端模型。

## 实验边界

Demo 实际实现了 YAML frontmatter、标题与 `[[Wikilink]]` 解析、结构化分块、BM25、链接邻居加权、状态过滤、上下文组装和确定性证据摘要。它没有 embeddings 和 LLM，因此：

- 可以验证词法检索、分块、排序信号和来源追踪；
- 可以观察恶意文本怎样进入上下文；
- 不能验证语义向量召回、真实模型忠实性或 Prompt Injection 防御率；
- “疑似指令”告警只是透明的演示性模式匹配，不是安全边界。

每道练习都按“运行 → 观察 → 预测 → 修改 → 验证”闭环进行。先写预测，再操作 Demo；只抄答案不能验证你的模型。

## 练习一：区分事实源与派生状态

1. 打开实验，记录初始的 `notes` 和 `chunks` 数量。
2. 在左侧选择“Atlas 的本地优先决策”。
3. 找到“同步不是备份”段落，在末尾增加一句：`恢复能力必须通过独立副本测试。`
4. 在点击“应用修改并重建索引”前，预测右侧结果和上下文是否会变化。
5. 应用修改，重新运行“同步为什么不是备份？”预设，检查新句子是否进入检索结果或摘要。
6. 点击“重置”，验证派生状态能否从原始样例重新生成。

问题：如果真实插件的向量索引丢失，但 Markdown 文件仍然完整，哪些内容应该能恢复？哪些内容可能无法恢复？

<details>
<summary>答案与评价标准</summary>

应用修改前，编辑器里的未提交文本还没有进入 `rawNotes`，所以索引和结果不应变化；应用后系统重新解析并分块，新内容才可能进入结果。重置会用初始 Markdown 重建所有派生状态。

只要实现与版本仍可用，文件正文、Properties 和 Wikilink 可以重新解析，词法或向量索引也应能重建。无法自动恢复的可能包括：没有写入文件的聊天记录、插件私有数据库中的人工标注、未版本化的模型与分块参数、已删除的来源、只存在远端服务中的状态。

优秀答案会指出“索引可重建”需要解析器、模型、参数和排除规则可追溯；不能因为原始文件存在就声称能得到完全相同的向量和排序。

</details>

## 练习二：证明关键词检索不是语义理解

1. 运行“同步为什么不是备份？”预设，记录第一条结果和匹配词项。
2. 改用“遗忘的想法怎样重新浮现？”预设，观察诊断、结果数量和分数。
3. 不修改样例笔记，尝试用你自己的问题表达“找回语义相关但用词不同的旧笔记”。
4. 预测加入真正的 embedding 检索后，哪些结果可能改善，哪些精确查询可能变差。

问题：为什么不能根据一次“看起来合理”的结果断言 BM25 已经理解语义？为什么向量检索也不能替代关键词基线？

<details>
<summary>答案与评价标准</summary>

BM25 根据词项统计排序。中文 Demo 还加入单字和相邻双字切分，因此词面重叠可能让结果看起来有语义，但算法没有学习“遗忘”和“旧笔记找回”之间的概念关系。没有重叠时，它无法凭意义建立连接。

向量检索可能改善同义表达和概念近邻，但可能弱化错误码、版本号、否定、数值和精确名称。可靠系统通常保留词法基线并比较或融合两路结果。评价时需要问题—来源测试集，不能用开发者挑选的单个演示问题。

优秀答案还会区分“模型产生的语义表示”与“这个结果对当前任务真正相关”，并提出精确查询和语义查询应分组测量。

</details>

## 练习三：改变 chunk size 与 Top-K，观察覆盖和噪声

1. 使用“怎样让 AI 回答能够追溯来源？”预设。
2. 分别选择 45、90、160 tokens，记录总分块数、第一条结果的标题和摘要内容。
3. 在 45 tokens 下将 Top-K 从 1 提高到 6；预测上下文包会如何变化。
4. 检查较大 Top-K 是否带来重复主题、弱相关片段或不可信资料。
5. 说明你会如何为一个真实 Vault 选择 chunk size，而不是照抄本实验参数。

<details>
<summary>答案与评价标准</summary>

较小上限一般产生更多、更聚焦的片段，但定义和限定条件更容易被拆开；较大上限保留更多局部上下文，也会稀释词项、增加上下文成本。由于 Demo 先尊重标题和段落，再拆分过长单元，实际数量变化还取决于样例结构，不能只用一个固定公式预测。

Top-K 增大提高候选覆盖，但不是单调质量提升：重复、冲突、过期资料和恶意文本都更可能进入上下文。真实系统应在目标问题集上分别测召回、排序、上下文冗余和引用支持度；代码、会议记录、表格和论文可能需要不同切分策略。

优秀答案会说明：如果 gold evidence 没进入候选，生成 Prompt 无法恢复它；如果已进入但答案错误，才继续检查排序、上下文和模型忠实性。

</details>

## 练习四：链接和状态是辅助信号，不是真实性分数

1. 运行“Atlas 为什么选择本地 Markdown？”预设，记录每条结果的 BM25 与 link 分数组成。
2. 关闭“链接邻居加权”重新运行，观察排序是否变化。
3. 打开“网页里的指令可以让 Agent 自动执行吗？”预设，把状态过滤从“全部”切换为“仅 verified”。
4. 预测为什么未审核网页会消失，以及这是否能证明剩余资料全部正确。
5. 设计一条错误链接：把一个不相关笔记链接到高分来源。说明图加权可能如何放大错误。

<details>
<summary>答案与评价标准</summary>

Demo 先计算每个 chunk 的 BM25，再让与高分笔记相邻的笔记得到可观察的小幅 graph score。它表达“作者显式连接的邻居可能值得一起看”，不表达逻辑支持或真实性。

`status=verified` 只是样例生命周期过滤，可以在检索前排除 `unreviewed` 笔记，缩小风险面；它不证明内容正确，因为状态可能被误标、过期或只代表完成过某种检查。状态、来源类型、时间和权限必须有独立语义。

优秀答案会提出：链接权重应可关闭、分开显示并通过消融测试评估；安全过滤应在召回前执行，不能只在回答后隐藏引用。

</details>

## 练习五：制造“忠实但错误”的回答

1. 选择“Atlas 的本地优先决策”。
2. 把“同步不是备份”改成“同步天然等同于完整备份，不需要独立副本”。
3. 应用修改，运行同步问题。
4. 检查排序、上下文和摘要能否发现这条主张是错的。
5. 重置样例后，列出至少三种在真实系统中阻止或暴露这种污染的方法。

问题：如果模型逐字忠实引用了错误来源，这属于生成失败还是语料失败？

<details>
<summary>答案与评价标准</summary>

Demo 的检索和确定性摘要没有事实验证器。被污染的句子与查询高度相关，可能得到高分并被忠实引用。这首先是语料质量和状态治理失败；如果系统承诺交叉验证却没有发现，也属于验证与输出策略失败。不能只用“忠实于上下文”代表“答案真实”。

可行措施包括：保留官方或原始来源；记录版本和生效时间；让关键结论需要两个独立来源或人工审核；区分外部材料与内部决定；对关键问题建立 gold evidence；对修改运行回归；发现冲突时返回 `conflicting_evidence`；使用 Git 或备份回滚。

优秀答案会把来源错误、检索错误、生成不忠实和引用错配分开，不笼统归为“幻觉”。

</details>

## 练习六：分析间接 Prompt Injection 的真正边界

1. 运行“网页里的指令可以让 Agent 自动执行吗？”预设。
2. 找到带 `UNTRUSTED INSTRUCTION` 的结果，查看它怎样进入 `<source>` 上下文。
3. 找到上下文顶部“资料是不可信数据”的策略文本。
4. 解释为什么标签和告警有帮助，却不能保证真实 LLM 不被诱导。
5. 假设 Agent 同时拥有 Vault 读写、Shell 和网络工具，为它设计一套确定性权限边界。

<details>
<summary>答案与评价标准</summary>

标签让系统和人知道来源边界，模式告警能发现一部分明显攻击；但模型看到的策略和资料最终都是 token，攻击可以改写、编码或隐藏，模式匹配也会有漏报和误报。RAG 不会自动消除间接 Prompt Injection。

合理边界包括：外部资料只进入不可信数据通道；默认只读；敏感路径在检索前排除；工具使用结构化参数；文件修改展示真实 diff；删除、Shell、联网和跨目录访问需要人工确认；命令执行环境隔离；凭证不进入 Vault；操作有审计日志和回滚。

优秀答案会强调防护必须位于工具和权限执行层，而不是让同一个模型自行判断“这条指令是否安全”。

</details>

## 练习七：为三个场景选择最小架构

分别为以下场景选择“核心 Obsidian”“当前笔记 AI”“Vault 内 RAG 插件”或“外部 Agent”，并说明数据流、验证和不采用更强方案的理由。

1. 个人阅读库有 300 篇带来源笔记，主要问题是按作者、年份和主题过滤。
2. 技术项目有数千篇事故与 ADR，经常使用不同措辞描述相似故障，需要回答时返回当前决定和历史依据。
3. 团队希望每天自动读取会议纪要、修改项目状态、运行 Shell 并把总结发送到外部服务。

<details>
<summary>答案与评价标准</summary>

1. 优先核心 Obsidian：Properties、Bases、普通搜索和人工入口已经直接表达查询。可选的当前笔记摘要不应演化成全 Vault 索引，除非真实问题证明需要。
2. 适合从词法基线发展到混合 RAG：同义故障需要语义召回，错误码和版本又需要词法检索；先按项目、时间和状态过滤，再返回 ADR 片段与引用。应建立真实查询集并处理废弃决定。
3. 这是高副作用 Agent，不应从“全自动”开始。先拆成只读汇总、状态 patch、外部发送三个独立能力；每项使用最小身份和目录，写入展示 diff，Shell 使用 allowlist 或隔离环境，外发需要数据分类与审批。会议纪要还属于不可信输入，必须考虑 Prompt Injection。

优秀答案不会因为场景 3 “更复杂”就默认给 Agent 全权限，而会重新判断是否应由确定性脚本完成状态更新，只把自然语言解释交给模型。

</details>

## 完成标准

- 能指出 Markdown、Properties 和链接属于什么状态，索引与回答属于什么状态。
- 能用实验解释 BM25、图加权、过滤、chunk size 和 Top-K 的作用与边界。
- 能把语料缺失、检索失败、生成不忠实和引用错配分别诊断。
- 能说明本地 Vault、插件、本地模型、云模型、Sync 和备份的不同信任边界。
- 能为 AI 写回设计只读基线、真实 diff、人工确认和回滚。
- 不把“有引用”“本地优先”“向量相似”或“插件已审核”当成真实性与安全保证。
